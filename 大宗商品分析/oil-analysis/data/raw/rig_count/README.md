# rig_count 数据缓存清单（Baker Hughes Worldwide Rig Count）

本目录存放「Worldwide Rig Count（全球旋转钻井平台数）」的 Excel 缓存。
来源页：`https://rigcount.bakerhughes.com/intl-rig-count`（页面顶部「Worldwide Rig Count Report - New Report」一行即当前最新期次）。

> ⚠️ **文件名**
> - 脚本自动发现下载的文件以 `uuid + ".xlsx"` 命名，`rig_count.py:129` 用它做缓存键，**勿物理重命名**（改名会破坏缓存命中 → 重复下载或变成孤儿文件）。
> - 人工下载的文件可直接用官方原名（如 `October-2026  WorldWide Rig Count Report.xlsx`）；本地兜底会连同 uuid 文件一起扫描，**命名不影响解析**，但合并顺序按「期次」而非文件名决定（见下）。

## 合并逻辑（rig_count.py，2026-10-07 修订）

1. **主干先合并**（1975-01 ~ 2024-03，`Total World` 官方合计列）。
2. **月度报告只取「期次最新的一份」后合并**（当前 = 2026-10 期，覆盖 2024-01~2026-10），覆盖重叠月份。
3. 输出 `data/processed/rig_world.json` → `{months, world, unit, source, latest_month, ...}`。

⚠️ **为什么不能把所有月度报告都叠加**：目录里同时存在 2026-06 / 2025-07 / 2026-10 三期月度报告，覆盖范围大量重叠但细项口径随期次变动。实测若逐份按文件名排序 update，2025-07 期会回写 2013-01~2025-07 共 116 个月，个别月份偏差达 47.6 台。故改为按「自身最新月份」挑一份。

## ⚠️ 已知口径断裂：2024-01 起 +263 台

序列在 **2023-12 = 1,739 → 2024-01 = 2,002**（+15%）有一处台阶，原因不是抓取错误，而是口径变化：

- 2026-09 期报告的 `WW Monthly` 明细带 `Rig Status` 列，取值有 **Active Rigs** 与 **Operating Rigs** 两种；后者的 132 行**全部来自 SAUDI ARABIA**（2024-01 起每月约 233–307 台）。
- 该报告自己的 `WW Summary` 明确 **Worldwide = Active + Operating 的合计**：2026-09 = 1,919.25、2026-08 = 1,906.8，与明细全量求和（1,919.2 / 1,906.8）完全吻合；只算 Active 会得到 1,657.2，明显不对。
- 而 2024-03 期的旧主干与 2025-07 期的旧报告都**不含**沙特的 Operating 行，2024-01 均给出约 1,783–1,784。

**结论**：2024-01 之后的数值含沙特 Operating Rigs，之前不含 → 两段**不可直接比较**。旧文件没有 Operating 明细，无法把 1975–2023 重算到新口径。

## ✅ 处理决定（2026-10-07）：选①——图上标注断点 + 数据源行注明

数值**不做任何改动**（保持与官方 `WW Summary` 一致），只在呈现层说明：

1. **图上标注**：`dashboard.js:rigWorld()` 在近 10 年格加一条 2024-01 竖向 markLine，橙色虚线 + 「口径调整」标签（概览格里 2024-01 已贴在右边缘，标注无意义故不加）。
2. **数据源行**：rig 卡片的 `.src` 增补「口径提示」一行，写明并入沙特 Operating Rigs（约 +263 台）、官方 Worldwide = Active + Operating、前后两段不可直接比较、+15% 为口径台阶而非真实跳升。
3. **文档**：主 `README.md` 供给侧表格的 World Rig Count 行同步注明。

未选②（Active-only）的原因：会让 2026-09 从 1,919.2 掉到 1,657.2，与官方 Summary 矛盾，对外引用需额外说明，得不偿失。
